## Artisan Response to Architect

**Their position:** Build the data spine first (`mce.formats/1` registry plus append-only, hash-bound `mce.run/1` manifest), express all post-production as optional `mce.timeline/2` fields (`transitions[]`, `gfx[]`, `audio.duck`, `grade`), and land new formats and look work only after that, with per-format quality bars carried as registry `qa`/`review` gate ids.

**My response:** Modify

**Reasoning:** I concede the order. The run manifest is the only thing that makes a look file, a contrast verdict or a transition check count, because review today never reads QA output (`qa-video.mjs` prints to stdout with no schema id or hashes), so a contrast gate added before `mce.qa/1` and `mce.run/1` exist would be one more unbound report. I also accept that the registry, not the look, decides *which* visual gates a format must pass: `qa: ["contrast", "type_floor", "transition_parity", "carousel_seam"]` belongs in the `FormatRow`. Where I hold the line is the idea that the look itself is a registry column. The registry is per format and committed; the look is per brand and per run, compiled from a brand kit that holds client data and must live in the gitignored run dir. Those have different owners, change at different rates and have different privacy rules, so `mce.look/1` stays its own schema id. The fix costs Architect nothing structurally: it is one more `FileRef` (`role: "look"`, `schema: "mce.look/1"`) written by `run plan` and listed as an input of `render` and `qa`, so the same hash rule that binds the timeline binds the look. The contrast check can also be built in the parallel wave without touching `render.mjs`/`runtime.js`: a pure module like `placement-zones.mjs` (input: text box, text colour, background luminance samples; output: ratio and verdict) with vitest fixtures (white-on-white FAIL, plated caption PASS), wired into `render --mode check` only at Architect's step 4, under the Q1 CI rule. On transitions, the loose B7 shape is not enough for two reasons I checked in the code. First, the vocabularies disagree: B7 proposes `cut|dissolve|dip|whip|match|wipe`, while the runtime implements `data-trans-in="cut|fade|dip|slide|zoom"` with `dip` as the default (`runtime.js:11,63-64`), so `timeline emit` would write kinds the renderer silently treats as something else. The timeline enum has to be the runtime enum, extended in both places in one change, and the emitted default has to be `cut`, not the runtime's implicit `dip`. Second, `dur: number` lets any value through. It should be one of the frame-based motion scale steps (4 f, 8 f, 0.35 s, 15 f at the 30 fps timeline clock), with a named easing token, so `timeline check` can fail a 0.9 s dissolve the same way it fails a transition on a non-cut point. The SFX binding needs no new field: `audio.sfx[].at` in `mce.timeline/2` is already a `ref()` (`timeline/schema.mjs:134`), so the rule is one `timeline check` line: a `whip`/`slide`/`zoom` transition at point P needs an sfx whose `at` refs P, and every transition window is passed to `qa-video` as a declared exemption so `transitions.at_cuts` stops flagging an intended crossfade and still fails any undeclared blend. `gfx[].enter` should likewise be a motion token from the same scale, not a free string. Net: spine first, look second as a hash-bound stage artifact, contrast built in parallel as a pure module and wired with step 4, transitions tightened to runtime enum, scale durations and point-bound SFX.
